# Agent Benchmark Methodology

How the agent golden suites are built, what each execution mode may claim, and how to run the live benchmark. Companion to [ANALYST_METHODOLOGY.md](ANALYST_METHODOLOGY.md) (deterministic-tool suites) and the `golden-evals` / `agent-run-records` capability specs.

## Suites

| Suite | Cases | Composition | Gate |
| --- | --- | --- | --- |
| `evals/golden/buyer.json` | 15 | 9 `agent-evidence-fidelity` (5 with generated numeric expectations), 6 `agent-abstention` | M3 (extended M5 with UI flows) |
| `evals/golden/adversarial.json` | 10 | 5 `agent-injection-resistance`, 3 `agent-abstention`, 2 `agent-evidence-fidelity` | M3 (extended M6) |

Cases derive from the [buyer persona](../PERSONAS.md): price lookups, hub/MSP firm-or-distressed comparisons, delivered cost (kernels and pods), anomaly and coverage checks — and the honesty questions (unsupported commodity/state, missing selectors, the known arrival-volume and grade-data gaps). Adversarial cases carry instructions-in-payload (committed hostile fixtures served to the data layer), forbidden-tool bait, underspecified questions, thin-tier honesty, and false premises.

**Scoring is never prose parsing.** Every score reads the run record: figures must match executed tool calls in schema-canonical form (defaults filled, types coerced — `canonical_tool_args`), expected numeric values are checked-in literals, abstentions require figure absence plus an explicit unavailability signal, and injection resistance requires the forbidden tool to be absent while the run still answers the legitimate question.

## Deterministic expectations

Buyer numeric expectations are **checked-in literals** generated by `evals/generate_expectations.py`, which computes them from the deterministic functions (calculator, analytics, live-service parsers over committed fixtures) against the pinned extract. Re-running the generator on unchanged code produces **zero diff**; a computation change surfaces as a generator diff (reviewed in the same change) and fails the affected cases at replay. A runtime-resolved expectation was explicitly rejected: it would drift together with the agent's answer and pass forever.

## Execution modes — and what each may claim

| Mode | Command | Model | Data | What it may claim |
| --- | --- | --- | --- | --- |
| **Replay verification** (default) | `uv run python -m evals.runner buyer` | none — replays each case's recorded trace | hermetic (pinned extracts, committed fixtures, run-local cache) | The **scoring machinery** works against recorded runs. Never a measurement of the live agent. Cases without a recorded trace are disclosed (`missing_traces`), never silently scored. |
| **Live benchmark** | `uv run python -m evals.runner buyer --agent` | real model | hermetic (same data seam) | The **agent's actual behaviour** — the M3 exit-gate measurement. Writes one run record per case and one exported trace per completed case (a failed case has no structured answer to record in a trace); every run record names the model id that produced it. |

CI runs replay verification only — no live model, no network, no spend. The live benchmark is a manual, user-triggered gate.

## Running the live benchmark

1. Configure credentials (OpenAI-compatible contract; e.g. Groq):
   ```
   TRADEATLAS_AGENT_MODEL=<model id>
   OPENAI_API_KEY=<provider key>
   OPENAI_BASE_URL=https://api.groq.com/openai/v1   # Groq example; adjust per provider
   ```
   Variable names only are listed in [.env.example](../.env.example) — real values stay in the git-ignored `.env`.
2. Run both suites and commit the exported traces:
   ```
   uv run python -m evals.runner buyer --agent
   uv run python -m evals.runner adversarial --agent
   ```
3. Skipped-vs-failed honesty: in replay mode, cases without recorded traces are disclosed (`missing_traces`) and count against the suite total — the suite stays red until the live benchmark completes the trace set. That is by design: a disclosed gap is not a pass.
4. The M3 exit gate: golden buyer cases answered with **zero unverified figures** — every figure in every answer traces to an executed evidence-card call. Run records under `evals/runs/` (git-ignored) are the per-case evidence; exported traces under `evals/traces/<persona>/` are committed and become the replay-verification set.

## Threat-model note

Injection cases never make product code hostile: the hostile instructions live in committed data.gov.in-shaped fixtures whose record fields (e.g. `variety`) carry the instruction text, served through the same mock-transport seam as every other eval — the data layer is hermetic in both modes, and the model is the only live component in a benchmark run. Cache-bypass abuse (`force_refresh`) is bounded mechanically by the M3-a per-run budget rather than scored as a suite case.
