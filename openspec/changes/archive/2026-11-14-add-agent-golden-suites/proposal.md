# Proposal

## Why

M3-a built the agent and its run records, but nothing measures it: the M3 exit condition — "golden buyer cases answered with zero unverified figures; run records produced for every benchmark run" — has no buyer cases and no agent benchmark. The analyst suite gated M2's deterministic tools; the agent needs its own measurable bar before M3-c (HITL) builds on it and before M3-d can judge specialists against a scored single-agent baseline. This is the measurement slice of the promotion gate.

## What Changes

- Add two golden suites: `evals/golden/buyer.json` (exactly 15 cases — 9 `agent-evidence-fidelity` with 5 numeric, 6 `agent-abstention`; investigation queries from the buyer persona: prices, hub/MSP comparisons, delivered cost, anomalies, coverage, honesty about what the data cannot say) and `evals/golden/adversarial.json` (exactly 10 cases — 5 `agent-injection-resistance`, 3 `agent-abstention`, 2 `agent-evidence-fidelity`; instruction-in-payload via hostile fixtures, forbidden-tool bait, underspecified questions, thin-tier honesty, false premises).
- Extend the golden-eval runner with agent execution: three new scoring kinds scored from the M3-a run record — figures matched to executed tool calls in schema-canonical form, abstentions signalled explicitly, forbidden tool calls matched by name — never from prose parsing. Agent kinds route before the resolver dispatch.
- Two execution modes, honestly separated: **live benchmark** (`--agent`, requires `TRADEATLAS_AGENT_MODEL` plus standard OpenAI-compatible credential variables — the user's Groq key works via `OPENAI_BASE_URL`; no provider-specific code) runs the real model against hermetic data — committed fixtures, pinned extracts, and a run-local cache — writing a run record + exported trace per case; **replay verification** (default, CI-safe) replays each case's recorded trace through the graph and scores it — machinery regression, explicitly not a measurement of the live agent.
- Deterministic agent expectations: numeric expectations are checked-in literals generated by extending the existing `evals/generate_expectations.py` (computed from the deterministic functions against the pinned extract; re-running on unchanged code yields no diff).
- Trace export: benchmark runs save each case's trace in the M3-a replay format under `evals/traces/<persona>/`; recorded traces are committed fixtures that feed replay verification.
- A short benchmark methodology doc (persona derivation, the two modes and what each may claim, the credential contract, how to run the live benchmark).

Out of scope (later M3 slices): HITL clarification via `interrupt()` (M3-c), multi-agent specialists and the deterministic verifier with the promotion-gate comparison (M3-d) — this change's fidelity matching is post-hoc offline scoring, not the in-run verifier — and methodology RAG (stretch).

## Capabilities

### New Capabilities

(none)

### Modified Capabilities

- `golden-evals`: new agent-case kinds with run-record-based scoring rubrics; agent execution modes (live benchmark / replay verification) with the hermetic-data rule; the buyer and adversarial suites at this gate.
- `agent-run-records`: trace export — a benchmark run can be recorded as per-case trace files in the existing replay format (the M3-a format gains its producer).

## Impact

- Code: `evals/runner.py` (agent routing before resolver dispatch, new scorers, case validation for agent kinds, both modes), `tradeatlas/agent/replay.py` (trace save), `evals/generate_expectations.py` (extended), suite JSONs, committed hostile-payload and trace fixtures, tests (`tests/test_agent_benchmark.py` + extensions).
- Reused unchanged: the seven agent tools, run records, `AgentAnswer`, resolver registry, `canonical_tool_args`, hermetic transport/cache fixture mechanisms (prebound runner-side; the DuckDB cache is pinned to a run-local temp dir so benchmark runs never read or write the developer's cache).
- Running the live benchmark requires `TRADEATLAS_AGENT_MODEL` plus OpenAI-compatible credential variables (the user's Groq key via `OPENAI_BASE_URL`) and consumes tokens — a manual, user-triggered step documented as the M3 exit-gate measurement; CI never runs a live model and never pays for one. `LANGSMITH_API_KEY` stays inert (plugin suppressed; no tracing code).
- `docs/ROADMAP.md` status section updated when the suites pass; the live benchmark run is the follow-up manual gate after apply.
